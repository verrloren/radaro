# Writing drafts that don't read as spam

## Principles

- **Answer the thread first, mention the product second.** A reply has to help even if the reader never clicks the link.
- **Disclose.** "Disclosure: I built this", "I'm the author", "I maintain X". Undisclosed self-promotion gets posts removed and accounts banned.
- **Be specific.** Use real numbers, real features and the real trade-offs. Say what the product does NOT do.
- **Match the room.** Use each community's vocabulary and depth; technical subreddits want details, Bluesky wants one sharp idea.
- **One link, at most.** Put it at the end and skip URL shorteners.
- **No hype words:** "revolutionary", "game-changing", "🚀🚀🚀", ALL CAPS, "check it out!!!".
- **Write like a person:** first person, plain sentences, no marketing template. Vary the openings between drafts.

## Angle per audience

Pick the angle that matters to that community, not the one that sounds best to you:
- **self-hosting:** privacy, no account, runs on your box, resource use, Docker or single binary;
- **Linux / CLI:** one static binary, Unix-friendly flags, `--json`, works over SSH;
- **developers:** architecture, stack, why it's built this way, what was hard;
- **indie / SaaS:** the problem, the cost versus alternatives, the story;
- **local AI:** runs offline, model-agnostic, no data leaves the machine.

## Shapes

**Reply to "what do you use for X?"**
> I've been dealing with the same thing. <One sentence on how the problem shows up>. I ended up building <name> for it: <what it does in one line>, <1–2 concrete details>. It doesn't do <limitation>, so if you need that, <honest alternative> is better. Disclosure: I'm the author. <link>

**Reddit launch post**
- Title: say what it is, e.g. "I built a self-hosted <thing> that <does X> — <key property>". No clickbait.
- Body:
  1. the problem, 2–3 sentences;
  2. what you built and how it works;
  3. what's different, and the honest limitations;
  4. the stack, if the sub is technical;
  5. a link;
  6. a genuine question for feedback.

**Bluesky / Mastodon announcement (≤ 300 / ≤ 500)**
> <What changed, in one line>. <Why it matters, in one line>. <link> #Tag1 #Tag2

**Dev.to article**
- Title: a lesson or a how-to, not a product name ("How I …", "What I learned building …").
- Structure:
  1. the problem;
  2. the approach, with code or diagrams;
  3. results and numbers;
  4. the trade-offs;
  5. a link to the project at the end.

## Before saving a draft, check

- Would this still be useful with the link removed?
- Is it disclosed, and is it within the platform's length limit?
- Is it different from every other draft in this batch?
- Does it follow the target community's rules?
